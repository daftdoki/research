# QNAP QuTS API-driven VM management — Notes

## Goal

Find tools that let you create and maintain VMs on a QNAP NAS running QuTS hero
(Virtualization Station) through an API, the way you would on a cloud
(declarative create, image + cloud-init, lifecycle, snapshots, teardown).

## Work log

### Is there an official API?

- Searched for official Virtualization Station (QVS) REST/Swagger docs. None
  found. QNAP publishes Swagger for QVR Pro (`download.qnap.com/apidoc/qvrpro/`)
  and a Container Station API doc (`qnap-dev.github.io/container-station-api`),
  but nothing for QVS. Every QVS how-to on qnap.com is web-UI only.
- QNAP forum thread t=169909 ("Virtualization Station (VM) controll via API")
  turned up in search but returns 404 to WebFetch now. Search snippet shows the
  only code in it was a Synology example — no QNAP answer.
- Tried the QTS HTTP API Authentication v5.1.0 PDF cited by the MCP server
  (`eu1.qnap.com/dev/QTS_HTTP_API-Authentication_v5.1.0.pdf`) — 404. So the
  only *official* piece of the stack (auth) is not currently reachable at that
  URL.
- Latest VS release notes found: 4.1.0.327 (2025-10-09). Adds VM High
  Availability beta (QuTS hero h5.3.0+ only). No mention of API, CLI,
  cloud-init or templates.

Conclusion: QVS does have a REST API — it's what the web UI calls, mounted at
`/qvs/` — but it's undocumented and unsupported.

### Community tools found (GitHub search: "qnap virtualization", "qvs qnap", "qnap terraform")

Shallow-cloned four repos into the scratchpad to read source (not committed):

1. **tmeckel/qnap-qvs-sdk-for-go** — Go SDK generated by AutoRest from OpenAPI
   specs. `scripts/create-services.py` takes `--api-dir .../specification/<svc>/readme.md`
   but the specs themselves are *not* in the repo. Services: `auth`, `users`,
   `vms`. Grepped `WithPath` calls: ~60 endpoints — `/vms`, `/vms/{id}/start|shutdown|forceshutdown|reset|suspend|resume|clone|export|sync|ips`,
   `/vms/{vm_id}/disks|adapters|cdroms|snapshots|snapshots/{id}/revert|usbs|pci|gpu|graphics|vnc_token|serialports|share`,
   `/vms/import_*`, `/vms/check_iso`, `/vms/mac`, `/vms/states`.
   Last commit 2022-01-06. GPLv3 (samples repo). The samples README mentions
   `QNAPQVS_CLIENT_ID/SECRET/TENANT_ID` env vars — looks like template
   boilerplate copied from the Azure SDK, not real QVS auth.
2. **danisla/qvscli** — Go CLI (last commit 2018-06-26). Most "cloud-like" of the
   lot: `vm create --image <base.img> --user-data --meta-data --authorized-key --startup-script --network --mac --cores --mem`.
   It renders a `#cloud-config` template, builds a NoCloud ISO with
   `genisoimage -volid cidata`, uploads it plus copies the base image via the
   QTS **File Station** API (`func=upload`, `copy`), then POSTs `/qvs/vms`.
   Also does "disk snapshot" by copying the qcow image. README warns Ubuntu
   cloud images may hang on first boot due to `console=ttyS0` in grub.
   Pre-dates VS 4; endpoints probably drifted.
3. **arnstarn/mcp-server-qnap-qvs** — Python MCP server, v0.9.2, last commit
   2026-03-27, MIT, on PyPI/GHCR, also ships as a QPKG. Tested on QuTS hero
   h5.2.8 + VS 4.1.x. Read `qvs_client.py`: auth is
   (a) `GET /cgi-bin/authLogin.cgi?user=..&plain_pwd=..` → `NAS_SID`,
   (b) `POST /qvs/auth/login` (base64 password) → `csrftoken` + `sessionid`,
   then every call sends the three cookies plus `X-CSRFToken` and a `Referer`.
   Note: plain password in a GET query string — ends up in NAS access logs.
   `create_vm` POSTs JSON to `/qvs/vms` with hardcoded `cpu_model=Opteron_G2`,
   `video_type=qxl`, one qcow2 virtio disk, one virtio NIC on bridge `qvs0`.
   No cloud-init / image-based create — it creates a blank disk. Has
   clone/export/import OVA, snapshots, ISO download, resize disk, guest-agent
   IPs. Destructive ops gated on `confirm=true`.
4. **scttfrdmn/qnap-vm** — Go CLI v0.2.0 (2025-09-15), MIT. Does *not* use the
   REST API. SSHes in, finds `/QVS` or `/KVM`, exports
   `LD_LIBRARY_PATH=/QVS/usr/lib:/QVS/usr/lib64` and PATH, runs `virsh`.
   `CreateVM` writes domain XML to `/tmp/<name>.xml` via heredoc and runs
   `virsh define`. Snapshots/clone/stats/console via virsh. Phase 3
   (automation/provisioning) is unbuilt.
   Open question I could not resolve from sources: does a domain defined
   straight into libvirt show up / stay consistent in the QVS UI, which keeps
   its own database? Nothing I read confirms either way. Treat as risk.

### virsh on QNAP

- qnapclub.de blog (2020, comments to Oct 2025): same `/QVS/usr/...` exports;
  needs `sudo` or virsh lists nothing (May 2024 comment); on QTS 5.2 a
  commenter finds virsh under `/share/CE_CACHEDEV*_DATA/.qpkg/QKVM/usr/bin/virsh`;
  VMs are addressed by UUID; UUID changed after a migration.
- jamesmwatson/QNAP-VM-launcher: plain `virsh` connects to `qemu:///session`
  and shows nothing; must use `qemu:///system?socket=<QKVM libvirt socket>`.
  Doesn't print the literal path.
- Implication for Terraform's `dmacvicar/libvirt` provider over `qemu+ssh://`:
  plausible (libvirt URIs accept `socket=` and the provider supports ssh
  transport) but nobody documents doing it against QNAP. libvirt's ssh
  transport also needs a helper (`nc`/`virt-ssh-helper`) on the remote PATH,
  and QNAP's libvirt lives off-PATH. Untested; flagged as speculative.

### Terraform

- `mohamed-mfarag/qnap` (on Terraform Registry, v0.5.0) — **Container Station
  only** (containers/apps). No VMs.
- `hashneo/terraform-provider-qnap` (May 2026) — read-only data sources
  (system, volumes, pools, shares, iSCSI, snapshots, NICs, users, apps,
  containers). Tested QTS 5.2.7. No VMs, no resources. Useful as a reference
  for the `authLogin.cgi` → `sid` → `/api/v2/...` pattern.
- No Terraform provider for QVS VMs exists that I could find.

### Container Station LXD route

- **3v1n0/qnap-lxd-vm** (created 2026-10-22, very new): Container Station
  ships LXD 5.0.2 but can't run `--vm` instances: QNAP kernel lacks vsock, no
  OVMF, no qemu-img, QEMU lacks seccomp. This QPKG adds vsock modules built
  from QNAP GPL kernel source, a static QEMU 9.0.3, OVMF and helpers, after
  which `lxc init ubuntu:24.04 vm --vm` works. Verified on QTS 5.2.10
  (TS-X53II); QuTS hero not mentioned. No SPICE/VGA console.
- If LXD VMs work, LXD has a real documented REST API and cloud-init
  (`cloud-init.user-data`), plus a Terraform provider (terraform-lxd/lxd) —
  i.e. genuinely cloud-like. But: whether Container Station lets you set
  `core.https_address` and keep it is undocumented (search turned up only
  generic LXD docs). And VMs created there are invisible to Virtualization
  Station. Third-party kernel modules on a NAS = support/upgrade risk.

### Dead ends

- GitHub REST search via curl returned nothing (proxy/rate limit); GitHub MCP
  search worked.
- GitHub MCP `get_file_contents` is scoped to this repo only; used shallow
  `git clone` into scratchpad instead.
- Ansible: no QNAP VS collection or module. Only route is `ansible.builtin.uri`
  against the undocumented API, or `command` over SSH with virsh.
- Searched for cloud-init in VS release notes: nothing.
