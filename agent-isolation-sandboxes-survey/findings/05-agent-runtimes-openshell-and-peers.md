# Track 5: NVIDIA OpenShell / NemoClaw and other sandbox + policy agent runtimes

Research date: 2026-09-29. This track answers the question "What about Nvidia's open shell or other frameworks like that?"

Scope: agent **runtimes and harness wrappers** that pair an isolation boundary with a declarative policy or governance layer, with a focus on the 2026 wave of always-on "claw" personal agents (OpenClaw and its descendants). Tracks 1 to 4 already cover the plain sandbox platforms (E2B, Daytona, Docker Sandboxes, microsandbox, Leash, httpjail, agent-sandbox and others), so they are not repeated here.

Method: I read NVIDIA's docs as raw Markdown (the Fern docs site serves `.md` for every page), the GitHub READMEs through `raw.githubusercontent.com`, CVE records from the CVE.org API, and PyPI release metadata. Vendor pages were read with WebFetch. Anything that comes only from press or secondary sources is flagged. **[analysis]** marks my own inference.

---

## 0. Headline findings

1. **OpenShell is real, open source (Apache-2.0), and changing fast.** Its first PyPI upload was on 2026-03-10 ([PyPI openshell](https://pypi.org/pypi/openshell/json)). NVIDIA announced it with NemoClaw at the GTC keynote on **2026-03-16** ([NVIDIA press release](https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Announces-NemoClaw-for-the-OpenClaw-Community/default.aspx)). **0.1.0 shipped on 2026-09-25**, four days before this research, and 0.1.2 followed on 2026-09-28 ([PyPI](https://pypi.org/pypi/openshell/json)). 0.1.0 has many breaking changes and no in-place upgrade from 0.0.x ([upgrade guide](https://docs.nvidia.com/openshell/latest/upgrade/0-1-0.md)).
2. **The isolation underneath is layered and uses shared-kernel primitives by default.** The workload runs non-root with no capabilities under **Landlock** (filesystem) and **seccomp user-notification**, which intercepts every TCP connect and DNS lookup and hands it to a trusted **supervisor** outside the boundary. The supervisor applies an **OPA**-evaluated policy, terminates TLS, and injects credentials. The outer fence depends on the runtime: a Docker/Podman container with networking disabled, a Kubernetes pod with a NetworkPolicy, or a **libkrun microVM** (KVM/HVF) with no NIC ([architecture](https://docs.nvidia.com/openshell/latest/about/architecture.md); [support matrix](https://docs.nvidia.com/openshell/latest/about/support-matrix.md)).
3. **The "privacy router" from the launch is gone in 0.1.0.** The `openshell inference` commands, the route APIs, and the `inference.local` endpoint were removed. Model access now goes through provider profiles plus credential substitution at native endpoints ([upgrade guide](https://docs.nvidia.com/openshell/latest/upgrade/0-1-0.md)). **NemoClaw still pins OpenShell 0.0.116** and still documents `inference.local` ([NemoClaw blueprint.yaml](https://raw.githubusercontent.com/NVIDIA/NemoClaw/main/nemoclaw-blueprint/blueprint.yaml); [NemoClaw how-it-works](https://docs.nvidia.com/nemoclaw/latest/about/how-it-works.md)). As of today the two stacks are on different major lines.
4. **Observability is the strongest in this class.** OpenShell logs every network, HTTP (L7), process, filesystem-policy and config event as **OCSF v1.8.0** records. You can stream them through CLI/TUI or export them as OCSF JSONL for a SIEM. The gateway also logs policy mutations ([logging](https://docs.nvidia.com/openshell/latest/observability/logging.md); [OCSF export](https://docs.nvidia.com/openshell/latest/observability/ocsf-json-export.md)). **No OTel export is documented.** The gateway's log buffer is not persisted ([accessing logs](https://docs.nvidia.com/openshell/latest/observability/accessing-logs.md)).
5. **It already has a CVE history.** Six NVIDIA CVEs were published on 2026-08-25 against OpenShell versions 0 to 0.0.33, including two CVSS 9.9 flaws: a sandbox escape (CVE-2026-65093) and an incomplete deny-list in the provisioning API (CVE-2026-65083). An L7 REST policy path-traversal bypass (CVE-2026-65092, 8.5) was in the same batch ([CVE.org API](https://cveawg.mitre.org/api/cve/CVE-2026-65093)).
6. **The peers split into three groups.** (a) **Claw runtimes with their own sandbox**: OpenClaw's optional tool sandbox, NanoClaw's container-per-agent, IronClaw's WASM tools, and OneCLI's agent-per-person with a gateway. (b) **Policy/firewall layers without a real boundary of their own**: Microsoft Agent Governance Toolkit (in-process), Cisco DefenseClaw (hooks + gateway), Pipelock and agentsh (proxy/kernel-hook enforcement), agentgateway, Lasso MCP Gateway, and Invariant Gateway. (c) **Hosted per-session VM sandboxes**: AWS AgentCore Runtime (microVM per session) and Azure Container Apps dynamic sessions (Hyper-V). **Among self-hostable projects, only OpenShell combines a kernel boundary, a declarative egress/L7/credential policy, a formal policy prover, and SIEM-grade audit output in one piece.**

## 2. NVIDIA OpenShell

### 2.1 What it is, license, repo, dates
- NVIDIA describes it as "the safe, private runtime for fleets of autonomous AI agents... You declare what each agent can touch in a policy, and OpenShell enforces it." Repo: [github.com/NVIDIA/OpenShell](https://github.com/NVIDIA/OpenShell). License: Apache-2.0 ([README](https://raw.githubusercontent.com/NVIDIA/OpenShell/main/README.md)).
- Timeline: first PyPI upload `0.0.0a0` on 2026-03-10, `0.0.88` on 2026-07-21, `0.0.116` on 2026-08-28, `0.1.0` on 2026-09-25, `0.1.2` on 2026-09-28 ([PyPI JSON](https://pypi.org/pypi/openshell/json)). NVIDIA's press release of 2026-03-16 calls OpenShell "an isolated sandbox that adds data privacy and security to autonomous agents", and adds that features "will be offered on a when-and-if-available basis" ([press release](https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Announces-NemoClaw-for-the-OpenClaw-Community/default.aspx)).
- Components are written in Rust. The gateway, sandbox and prover ship as static musl binaries. SDKs exist for Python, TypeScript, Go and Rust ([README](https://raw.githubusercontent.com/NVIDIA/OpenShell/main/README.md); [support matrix](https://docs.nvidia.com/openshell/latest/about/support-matrix.md)).
- Release policy: weekly stable releases (Tuesdays). Stable interfaces stay backward-compatible across patches. Security fixes go to the latest minor and N-1 ([support matrix](https://docs.nvidia.com/openshell/latest/about/support-matrix.md)).

### 2.2 Architecture and isolation mechanisms
- **Gateway** is the control plane: identity, sandbox state, policy and settings delivery, providers, and the policy prover. **Compute driver** provisions a **workload** and a separate **supervisor**. The **supervisor** (trusted) makes every decision: it checks policy, supplies credentials, resolves DNS and opens upstream connections. The **sandbox** binary (inside the boundary, with the agent) "never makes policy decisions" ([architecture](https://docs.nvidia.com/openshell/latest/about/architecture.md)).
- **Inside the boundary (Linux backend):** "the workload uses one non-root identity and no Linux capabilities. Landlock limits filesystem access; seccomp user notification stages network operations. The sandbox identifies the calling executable from trusted process observations" (`/proc`) ([architecture](https://docs.nvidia.com/openshell/latest/about/architecture.md)).
- **Supervisor↔sandbox channel:** one mutually authenticated HTTP/2 connection (the "OpenShell Sandbox Protocol"). It runs over a Unix socket (Docker/Podman), TCP with mTLS (K8s) or vsock (microVM). **Fail closed:** launch is held until the supervisor confirms, and the agent is frozen if the connection drops. JWTs are bound per sandbox and per generation, and the sandbox holds only the gateway's public key ([architecture](https://docs.nvidia.com/openshell/latest/about/architecture.md)).
- **Outer fence per runtime** ([architecture](https://docs.nvidia.com/openshell/latest/about/architecture.md); [runtimes](https://docs.nvidia.com/openshell/latest/how-it-works/sandboxes/runtimes.md); [support matrix](https://docs.nvidia.com/openshell/latest/about/support-matrix.md)):

  | Runtime | Supervisor location | Direct egress blocked by |
  |---|---|---|
  | Docker (≥28) | own container | workload container has networking off |
  | Podman 5.x (rootless) | own container | same |
  | Kubernetes ≥1.29 (Helm) | own pod | NetworkPolicy; the "CNI must enforce NetworkPolicy" |
  | MicroVM (`vm` driver, **libkrun**; KVM on Linux, Hypervisor.framework on macOS) | host process | guest has no network device |
  | Windows MXC | "Coming soon" | n/a |

  K8s pods can also select a RuntimeClass (e.g. `kata-containers`) through driver config, but that is disabled by default and needs an operator to allow it ([runtimes](https://docs.nvidia.com/openshell/latest/how-it-works/sandboxes/runtimes.md)).
- **Kernel requirements (checked at startup):** Landlock ABI ≥3 (Linux 6.2+), seccomp with nested user-notif filters and `SECCOMP_IOCTL_NOTIF_ADDFD`/`SEND`, and task-memory access (`process_vm_readv/writev`). `WAIT_KILLABLE_RECV` (5.19+) is recommended. On older kernels such as RHEL 9 it runs in a reduced "legacy read-only" mode. On macOS these checks run in the Docker Desktop Linux VM ([support matrix](https://docs.nvidia.com/openshell/latest/about/support-matrix.md)).
- **Seccomp denylist** blocks `mount`, `pivot_root`, `move_mount`, namespace creation, `ptrace`, `process_vm_readv`, `pidfd_*`, `bpf`, `io_uring_setup`, `perf_event_open`, `seccomp` and `userfaultfd` ([best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)).
- **Host platforms:** Linux amd64/arm64 (Debian/Ubuntu), macOS Apple Silicon (Docker Desktop), and Windows WSL2 (experimental). GPUs pass through via NVIDIA CDI (Docker/Podman), `nvidia.com/gpu` (K8s) or one PCI GPU (microVM) ([support matrix](https://docs.nvidia.com/openshell/latest/about/support-matrix.md); [runtimes](https://docs.nvidia.com/openshell/latest/how-it-works/sandboxes/runtimes.md)).

### 2.3 Policy model
- A YAML file with `version: 1` and five sections ([policies overview](https://docs.nvidia.com/openshell/latest/how-it-works/policies/overview.md)):

  | Section | Enforced by | When |
  |---|---|---|
  | `filesystem_policy` | Landlock | sandbox start (static) |
  | `landlock` (best-effort toggle) | sandbox runtime | start (static) |
  | `process` (user/group) | Docker/Podman | creation (static) |
  | `network_policies` (destinations per binary + request rules) | sandbox network proxy | **live, hot-reload** |
  | `network_middlewares` | proxy | **live** |

- Evaluation: "OpenShell denies anything the policy does not allow". Network rules are keyed on host, port **and calling binary**. L7 rules can restrict HTTP method and path (e.g. read but not write). The engine is OPA ([policies overview](https://docs.nvidia.com/openshell/latest/how-it-works/policies/overview.md); [best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)). The best-practices page also documents an `audit` vs `enforce` mode per rule ([best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)).
- **Precedence:** a gateway-admin **global policy** comes first. It replaces sandbox policies and blocks sandbox-level changes and approvals. Next comes the sandbox's saved policy (`--policy`), then a policy baked into the image, then a restrictive default. Attached providers add their own network rules to form the "effective policy" ([policies overview](https://docs.nvidia.com/openshell/latest/how-it-works/policies/overview.md)).
- **Who can change policy at runtime:** operators, through `openshell policy update/set` or approval in the TUI. Filesystem and process sections need the sandbox to be recreated ([best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)). The **policy advisor** is off by default. When enabled, the *agent* can propose new **network** rules only, never removals or filesystem/process changes. Proposals wait for human review unless you opt into auto-approval for proposals where the prover finds no new risk ([advisor](https://docs.nvidia.com/openshell/latest/how-it-works/policies/advisor.md)).
- **Policy prover:** an SMT-solver-based check. It verifies that a policy stays within a boundary policy (`openshell-prover` CLI, which can run in CI). It also flags proposals that add credentialed reach, new HTTP methods or cloud-metadata access; any finding blocks auto-approval. NVIDIA notes its guarantees cover only "the policy features and behavior represented by its model" ([prover](https://docs.nvidia.com/openshell/latest/how-it-works/policies/prover.md); [architecture](https://docs.nvidia.com/openshell/latest/about/architecture.md)).

### 2.4 Egress and credential handling
- Every outbound connection goes through the CONNECT proxy and OPA. Deny-by-default ([best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)).
- **TLS termination is on by default.** The proxy peeks for a ClientHello and terminates TLS with a **per-sandbox ephemeral CA**. The CA is injected via `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `GIT_SSL_CAINFO` and others. Setting `tls: skip` on an endpoint turns off credential rewriting and L7 inspection for it ([best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)).
- **Providers:** a provider profile binds a credential to allowed hosts, ports, paths and **binaries**. Inside the sandbox the env var holds an opaque placeholder. The supervisor substitutes the real value "only at an endpoint authorized by that profile" ([inference](https://docs.nvidia.com/openshell/latest/how-it-works/inference.md); [first agent](https://docs.nvidia.com/openshell/latest/about/run-your-first-agent.md)). Credential storage defaults to encrypted DB storage, with a Kubernetes Secrets driver as an option ([upgrade guide](https://docs.nvidia.com/openshell/latest/upgrade/0-1-0.md)).
- **SSRF protection** covers cloud metadata (169.254.169.254) and DNS rebinding ([best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)).
- **Inference routing / "privacy router":** this was part of the GTC pitch ("agents can use frontier models running in the cloud" through a privacy router, per the [press release](https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Announces-NemoClaw-for-the-OpenClaw-Community/default.aspx)). **0.1.0 removed** `openshell inference`, the route APIs and `inference.local`. Workloads now call native provider endpoints, and credentials are substituted there ([upgrade guide](https://docs.nvidia.com/openshell/latest/upgrade/0-1-0.md); [inference](https://docs.nvidia.com/openshell/latest/how-it-works/inference.md)).

### 2.5 Supported agents
- 0.1.x: "OpenShell can run any agent that is available in a sandbox image". The default image is bare `nvcr.io/nvidia/base/ubuntu:24.04` with no agent CLIs and a network-denying fallback policy. The docs walk through OpenCode+OpenRouter and Pi ([first agent](https://docs.nvidia.com/openshell/latest/about/run-your-first-agent.md); [upgrade guide](https://docs.nvidia.com/openshell/latest/upgrade/0-1-0.md)). Profile IDs include `claude-code` and `github` ([upgrade guide](https://docs.nvidia.com/openshell/latest/upgrade/0-1-0.md)).
- 0.0.116 docs listed Claude Code (full default-policy coverage), OpenCode (partial), Codex ("No coverage", needs a custom policy), GitHub Copilot CLI, OpenClaw and Hermes (through NemoClaw), plus Ollama and Pi images from [OpenShell-Community](https://github.com/NVIDIA/OpenShell-Community) ([v0.0.116 supported agents](https://docs.nvidia.com/openshell/v0.0.116/about/supported-agents.md)).
- OpenClaw itself can use OpenShell as a sandbox **backend**, over SSH, with OpenShell ≥0.0.88 ([OpenClaw OpenShell docs](https://docs.openclaw.ai/gateway/openshell.md)).

### 2.6 Observability
- **Two log streams in one file:** Rust `tracing` for internals, and **OCSF v1.8.0** events for everything security-relevant: `NET:` (4001), `HTTP:` (4002), `SSH:` (4007), `PROC:` (1007), `FINDING:` (2004, e.g. proxy bypass, nonce replay), `CONFIG:` (5019, policy load/reload, Landlock, TLS, provider changes) and `LIFECYCLE:` (6002). Each event carries ALLOWED/DENIED, process (pid), destination and the matching policy name ([logging](https://docs.nvidia.com/openshell/latest/observability/logging.md)). Example: `OCSF NET:OPEN [MED] DENIED /usr/bin/curl(64) -> httpbin.org:443 [policy:- engine:opa] [reason:no matching policy]` (same source).
- **Access paths:** `openshell logs` (gRPC stream, loss-aware cursors), a **TUI** dashboard, and log files inside the sandbox (`/var/log/openshell.*.log`). The gateway keeps only a bounded in-memory buffer "not persisted to disk". The push channel "drops events rather than blocking" ([accessing logs](https://docs.nvidia.com/openshell/latest/observability/accessing-logs.md)).
- **SIEM export:** full OCSF JSONL can be toggled per sandbox or globally without a restart. The docs include schema-version downgrade for AWS Security Lake, Splunk and CrowdStrike ([OCSF export](https://docs.nvidia.com/openshell/latest/observability/ocsf-json-export.md)).
- **Policy decision audit:** gateway-originated policy merges and draft approvals/removals emit `gateway` OCSF `CONFIG:*` lines ([accessing logs](https://docs.nvidia.com/openshell/latest/observability/accessing-logs.md)).
- **Not found:** OpenTelemetry/OTLP or Prometheus export. A grep of the logging, OCSF, telemetry, architecture and security pages found no OTel mention. Anonymous product telemetry is on by default and can be disabled with `OPENSHELL_TELEMETRY_ENABLED=false` ([README](https://raw.githubusercontent.com/NVIDIA/OpenShell/main/README.md)).

### 2.7 Documented limitations and security caveats
- **Security CVEs** (CVE.org, published 2026-08-25, affected "0 to 0.0.33"): CVE-2026-65093 sandbox escape (9.9); CVE-2026-65083 incomplete deny-list in the provisioning API (9.9); CVE-2026-65091 OS command injection via a malicious gateway (8.8); CVE-2026-65092 path traversal bypassing the L7 REST network policy (8.5); CVE-2026-65086 command injection in the exec handler (6.8); CVE-2026-65085 output encoding issue in the inference proxy (5.2) ([CVE-2026-65093](https://cveawg.mitre.org/api/cve/CVE-2026-65093), [‑65083](https://cveawg.mitre.org/api/cve/CVE-2026-65083), [‑65092](https://cveawg.mitre.org/api/cve/CVE-2026-65092), [‑65091](https://cveawg.mitre.org/api/cve/CVE-2026-65091), [‑65086](https://cveawg.mitre.org/api/cve/CVE-2026-65086), [‑65085](https://cveawg.mitre.org/api/cve/CVE-2026-65085)).
- **The shared kernel is the real boundary** with the Docker/Podman/K8s drivers (Landlock + seccomp + container). Only the `vm` driver gives a hardware boundary, and the VM driver "is never auto-detected" ([runtimes](https://docs.nvidia.com/openshell/latest/how-it-works/sandboxes/runtimes.md)). **[analysis]** libkrun puts the VMM and guest in one security context (see Track 2), so the microVM path should itself be confined on the host.
- **Docker Desktop:** it "must have host networking enabled, and it cannot use Enhanced Container Isolation" ([runtimes](https://docs.nvidia.com/openshell/latest/how-it-works/sandboxes/runtimes.md)).
- **L4-only endpoints** (no request rules) allow any request once the connection is permitted. `audit` mode does not block. Broad binary globs (`/**`) defeat binary binding. Approving an endpoint "permanently widens the running sandbox's policy" ([best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)).
- **GPU + user namespaces:** "NVIDIA device plugin compatibility with user namespaces is unverified" ([best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)).
- **Local gateways** can leave JWT TTL unset, which gives tokens that live for the sandbox run. Disabling TLS or allowing unauthenticated users "must not be exposed to shared or public networks" ([architecture](https://docs.nvidia.com/openshell/latest/about/architecture.md); [best practices](https://docs.nvidia.com/openshell/latest/security/best-practices.md)).
- **Churn:** there is no in-place upgrade from 0.0.x. Every sandbox must be recreated, built-in provider profiles were removed, and the policy schema now rejects unknown fields ([upgrade guide](https://docs.nvidia.com/openshell/latest/upgrade/0-1-0.md)).
- **[analysis]** OCSF logs inside the sandbox are the complete record, but they live on the agent's side of the boundary. I found no statement that the agent cannot tamper with `/var/log/openshell*.log`. Ship JSONL off-box if the audit trail matters.

## 3. NVIDIA NemoClaw

- **What:** an "open source reference stack for running supported AI agents more safely inside NVIDIA OpenShell sandboxes": guided onboarding, managed inference, network policy, managed MCP/messaging integrations, snapshots and lifecycle. Supported agents: **OpenClaw (default), Hermes, LangChain Deep Agents Code**. License Apache-2.0. Self-described as "an alpha project" ([README](https://github.com/NVIDIA/NemoClaw)).
- **Announced** 2026-03-16 at GTC as a one-command install of Nemotron models plus OpenShell for "claws". Hardware named: GeForce RTX PCs/laptops, RTX PRO workstations, DGX Station and DGX Spark ([press release](https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Announces-NemoClaw-for-the-OpenClaw-Community/default.aspx)).
- **Layering:** NemoClaw "calls OpenShell APIs and CLI commands to create and configure the sandbox that runs OpenClaw" ([ecosystem](https://docs.nvidia.com/nemoclaw/latest/about/ecosystem.md)). Unlike OpenClaw's own sandbox, **the whole agent runs inside the sandbox**, not just its tools.
- **What it adds over `openshell sandbox create --from openclaw`:** a stricter policy layered on top; image hardening that removes `gcc/g++/make` and `netcat`; read-only `/usr /lib /etc`; automatic provider creation; filtering of host env secrets (API keys, Discord/Slack/Telegram bot tokens); a versioned, digest-verified blueprint; and snapshot/restore "with credential stripping and integrity checks" ([ecosystem](https://docs.nvidia.com/nemoclaw/latest/about/ecosystem.md)).
- **Platforms:** DGX OS on Spark is Tested. DGX Station GB300, macOS Apple Silicon (Colima/Docker Desktop) and WSL2 are "Tested with limitations". Linux/Ubuntu 24.04 is the primary path. It needs 8 GB RAM minimum and 16 GB recommended, and the image is about 2.4 GB compressed ([prerequisites](https://docs.nvidia.com/nemoclaw/latest/get-started/prerequisites.md)).
- **Version pin:** `min_openshell_version` and `max_openshell_version` are both `0.0.116`, and the SDK dep is `@nvidia/openshell-sdk 0.0.116` ([blueprint.yaml](https://raw.githubusercontent.com/NVIDIA/NemoClaw/main/nemoclaw-blueprint/blueprint.yaml); [package.json](https://raw.githubusercontent.com/NVIDIA/NemoClaw/main/package.json)). Its docs still describe `inference.local` and a host-side Model Router ([how-it-works](https://docs.nvidia.com/nemoclaw/latest/about/how-it-works.md)). **[analysis]** NemoClaw users are therefore on the 0.0.x line, which OpenShell 0.1 has already broken. Expect a migration.

## 4. Claw-style runtimes with their own sandbox

### 4.1 OpenClaw built-in sandboxing
- Sandboxing is **off by default**. When enabled, it covers **tool execution only**: "The Gateway process always stays on the host". The docs are candid: "This is not a perfect security boundary" ([OpenClaw sandboxing](https://docs.openclaw.ai/gateway/sandboxing.md)).
- Settings: mode `off | non-main | all`; scope `agent | session | shared`; backend `docker` (default) `| podman | ssh | openshell | crabbox` ([modes/scope/backend](https://docs.openclaw.ai/gateway/sandboxing/modes-scope-and-backend.md)).
- Docker defaults: `network: "none"`, `readOnlyRoot: true`, `capDrop: ["ALL"]`. `network: host` is blocked, and container namespace joins are blocked unless you set a `dangerously...` override ([docker backend](https://docs.openclaw.ai/gateway/sandboxing/docker-backend.md); [images and setup](https://docs.openclaw.ai/gateway/sandboxing/images-and-setup.md)).
- Escape hatch: `tools.elevated` runs `exec` outside the sandbox. Debugging is through `openclaw sandbox explain` ([sandboxing](https://docs.openclaw.ai/gateway/sandboxing.md)).
- Context, from secondary sources only: OpenClaw had a critical RCE (CVE-2026-25253), more than 135k exposed instances, and the "ClawHavoc" malicious-skills campaign, per [Cisco's DefenseClaw coverage](https://blogs.cisco.com/ai/cisco-announces-defenseclaw) and trade press. Not independently verified here.

### 4.2 NanoClaw
- A minimal personal agent built on the Claude Agent SDK. "Agents run in their own Linux containers with filesystem isolation, not merely behind permission checks... they can only see what's explicitly mounted." Docker runs on macOS/Linux/WSL2. License MIT ([README](https://github.com/qwibitai/nanoclaw)).
- Credentials: "agents never hold raw API keys. Outbound requests route through a credential gateway that injects credentials at request time and enforces per-agent policies and rate limits". The installer sets up **OneCLI's Agent Vault** by default (same source).
- The isolation model is about **data** separation between channels: a shared session, the same agent with separate sessions, or separate agent groups with separate containers ([isolation-model.md](https://github.com/qwibitai/nanoclaw/blob/main/docs/isolation-model.md)). There is no declarative network policy file beyond the gateway. Observability is minimal.

### 4.3 IronClaw (NEAR AI)
- A Rust re-implementation inspired by OpenClaw. **Untrusted tools run as WASM** with capability-based permissions (HTTP, secrets, tool invocation), endpoint allowlisting, host-boundary credential injection and **leak detection** on both requests and responses. It also has a Docker sandbox with per-job tokens. The README claims a "Full audit log of all tool executions" and a web gateway UI. License MIT OR Apache-2.0 ([README](https://github.com/nearai/ironclaw)).
- **[analysis]** WASM confines only the tools compiled to WASM. Shell and Docker jobs fall back to container isolation.

### 4.4 OneCLI
- "An open-source platform for running AI agents as a team": one sandboxed agent per person, "The only way out is the gateway". The Rust gateway "intercepts outbound requests (HTTPS included, via MITM) and injects credentials". Secrets are stored AES-256-GCM, or fetched on demand from Bitwarden/1Password. License Apache-2.0 with a CLA ([README](https://github.com/onecli/onecli)).
- The sandbox substrate is pluggable. "`docker/` is the only place a container runtime is named". Fly, k8s and microVMs are future backends ([runner README](https://github.com/onecli/onecli/tree/main/apps/runner)).

## 5. Policy / governance / firewall layers (no strong boundary of their own)

### 5.1 Microsoft Agent Governance Toolkit (AGT)
- Released 2026-04-02 ([Microsoft Open Source blog](https://opensource.microsoft.com/blog/2026/04/02/introducing-the-agent-governance-toolkit/)). MIT, "Public Preview", SDKs in Python, TypeScript, .NET, Rust and Go ([README](https://github.com/microsoft/agent-governance-toolkit)).
- Model: `govern(tool, policy="policy.yaml")` checks every call against YAML/OPA/Cedar, logs to a tamper-evident audit trail (Merkle), and adds identity (SPIFFE/DID/mTLS), "privilege rings", a kill switch and an MCP security gateway (same source).
- **Key caveat, from the README itself:** "AGT enforces governance at the application middleware layer, not at the OS kernel level. The policy engine and agents share the same process boundary." Microsoft recommends "a separate container for OS-level isolation". The repo includes an example layered on kubernetes-sigs/agent-sandbox ([README](https://github.com/microsoft/agent-governance-toolkit)).

### 5.2 Cisco DefenseClaw
- Launched 2026-03-23, alongside RSA 2026. Positioning: "OpenShell gives you the sandbox. Cisco gives you the scanners." It scans skills, MCP servers and code, and produces an AIBOM before anything runs. Blocking a skill revokes its sandbox permissions and quarantines its files ([Cisco blog](https://blogs.cisco.com/ai/cisco-announces-defenseclaw)).
- Implementation: a Python CLI, a Go gateway, **connector hooks** (Claude Code `PreToolUse`, Codex, OpenClaw via proxy, and others, "thirteen first-class connectors") with log/block/HITL modes ([docs](https://cisco-ai-defense.github.io/defenseclaw/docs/); [connector compatibility](https://cisco-ai-defense.github.io/defenseclaw/docs/connectors/compatibility/)). Apache-2.0 ([README](https://github.com/cisco-ai-defense/defenseclaw)).
- Observability is its strength: Splunk HEC, OTLP export and JSONL, with a "mandatory local SQLite" compliance floor ([observability](https://cisco-ai-defense.github.io/defenseclaw/docs/observability/)). The README says it "does not prove that an agent... is risk-free" ([README](https://github.com/cisco-ai-defense/defenseclaw)).

### 5.3 Pipelock
- "Open-source AI agent firewall". It inspects mediated HTTP, WebSocket, MCP and A2A traffic (and CONNECT contents when TLS interception is on) for secret exfiltration, prompt injection, SSRF and tool poisoning. It emits **mediator-signed action receipts** ([README](https://github.com/luckyPipewrench/pipelock)).
- `pipelock sandbox` gives optional unprivileged containment: "Linux uses Landlock and network namespaces; `linux/amd64` also applies seccomp", and macOS uses `sandbox-exec`. Modes are strict, balanced and audit. It works with Claude Code, Codex, Cursor, OpenCode and others (same source).
- Licensing: the source is Apache-2.0, but "pre-built release artifacts include paid-tier code". The fleet dashboard is Pro/Enterprise. Free observability covers Prometheus/Grafana for a single instance and JSONL/HTML reports (same source).

### 5.4 agentsh (Canyon Road)
- An "execution gateway" that sits *under* the agent and intercepts file, network, process and signal activity, including subprocess trees. Decisions are `allow/deny/approve/redirect/soft_delete`. It emits structured audit events. On Linux it probes for seccomp user-notify, Landlock, FUSE, eBPF, ptrace and cgroups. macOS ESF/NE support is alpha. Apache-2.0 ([README](https://github.com/canyonroad/agentsh)).
- It is an enforcement layer you can put *inside* a VM sandbox such as E2B or Daytona. The README notes that seccomp user-notify cannot install on some Firecracker-class hosts, and reports the reduced mode instead (same source).

### 5.5 agentgateway (Linux Foundation / AAIF)
- A proxy for MCP, A2A, LLM, HTTP and gRPC. Auth is JWT/API keys/OAuth. It has "fine-grained RBAC with CEL policy engine", guardrail webhooks (regex, OpenAI moderation, Bedrock Guardrails, Model Armor), and **OpenTelemetry metrics/logs/tracing**. It ships a built-in UI and a Kubernetes Gateway API controller. Apache-2.0 ([README](https://github.com/agentgateway/agentgateway)). It joined AAIF ([AAIF blog](https://aaif.io/blog/agentgateway-joins-aaif-as-an-open-gateway-for-agentic-ai-infrastructure)). No sandbox.

### 5.6 Lasso MCP Gateway and Invariant Gateway
- **Lasso MCP Gateway:** a pip-installable MCP proxy with guardrail plugins (e.g. token masking) and tracing plugins. MIT ([README](https://github.com/lasso-security/mcp-gateway)).
- **Invariant Gateway:** a "zero-configuration" LLM proxy (OpenAI/Anthropic APIs) that traces agent interactions into Invariant Explorer. Apache-2.0 ([README](https://github.com/invariantlabs-ai/invariant-gateway)). Snyk acquired Invariant Labs in June 2025 ([Snyk news](https://snyk.io/news/snyk-acquires-invariant-labs-to-accelerate-agentic-ai-security-innovation/)).
- Neither provides isolation. Both are observation and guardrail points for LLM or MCP traffic only.

## 6. Hosted per-session sandboxes (for comparison with the self-hosted options)

### 6.1 AWS Bedrock AgentCore Runtime and Code Interpreter
- Runtime: "Each user session... receives its own dedicated microVM with isolated Compute, memory, and filesystem... After session completion, the entire microVM is terminated and memory is sanitized". Sessions last up to 8 h on microVMs (14 days on Instances), with a default idle timeout of 15 min. AgentCore "does not enforce session-to-user mappings", so your backend must ([runtime sessions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html)).
- Code Interpreter: "runs in a containerized environment within Amazon Bedrock AgentCore". Network setting is Sandbox or Public, plus an IAM execution role. Default session timeout is 15 min, extendable to 8 h. CloudTrail logging is available ([code interpreter](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/code-interpreter-tool.html); [session mgmt](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/code-interpreter-resource-session-management.html)).
- Observability: CloudWatch dashboards; "AgentCore emits telemetry data in standardized OpenTelemetry (OTEL)-compatible format" ([observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html)).

### 6.2 Azure Container Apps dynamic sessions
- "Hyper-V isolation and optional network controls". Session pools come as built-in code-interpreter or custom-container pools ([sessions](https://learn.microsoft.com/en-us/azure/container-apps/sessions)).
- "By default, sessions are prevented from making outbound network requests". The management API is gated by the Entra "Session Executor" role. Managed identity inside a session is **disabled by default** and comes with a warning: "any code... in the session can create Microsoft Entra tokens". Logs go to Azure Monitor/Log Analytics, but only custom-container sessions emit AppEnvSession tables ([sessions usage](https://learn.microsoft.com/en-us/azure/container-apps/sessions-usage)).

## 7. Takeaways for homelab and SMB deployments **[analysis]**

- **To run an always-on claw at home with real guardrails**, NemoClaw on OpenShell is the most complete packaged option. But it is alpha and pinned to OpenShell 0.0.116, a line whose early versions had 9.9-severity escapes (fixed after 0.0.33). Run it on a dedicated box or VM. DGX Spark is the tested target.
- **For coding agents such as Claude Code, Codex or OpenCode**, OpenShell 0.1.x by itself (no NemoClaw) with the `vm` driver on a KVM host is the strongest self-hosted setup here. It combines a microVM boundary, Landlock/seccomp inside, per-binary egress policy, credential placeholders and OCSF logs. The price is a 4-day-old breaking release.
- **Governance layers** (AGT, DefenseClaw, Pipelock, agentsh, agentgateway) complement a sandbox and do not replace one. AGT says so explicitly. DefenseClaw is designed to sit on top of OpenShell.
- **For observability**, OpenShell (OCSF → SIEM), DefenseClaw (Splunk/OTLP/SQLite) and agentgateway (OTel) are the three that emit structured, standard-schema decision logs. Mixing them means translating between OCSF and OTel.
